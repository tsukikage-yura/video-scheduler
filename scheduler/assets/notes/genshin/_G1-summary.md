15 个实验，全部基于同一套**共享绘图库**（`g1src/lib.js`，约 25KB）：
拱形几何 + 装饰母题 + 建筑构件 + 透视相机。每个 `code/eNNN.html` 都是自包含单文件
（库被内联进 `<script>`），1920×1080，纯 Canvas 2D，无外部素材，无 `Math.random()`。

## 八条核心结论（"怎么做才能像原神那种画面"）

1. **拱形用两段二次贝塞尔，控制点必须落在顶点下方（m<1）。**
   `P1 = (cx − hw·0.55, springY − rise·0.76)`。m>1 会在顶点产生丑陋的过冲尖刺；
   纯二次贝塞尔（单段）又太"抛物线"、缺少哥特的"尖"。
   **这一个参数（m=0.76, k=0.55）决定了整组画面的"拱好不好看"。**

2. **天空/玻璃/墙面一律"平涂分段"，绝不用 createLinearGradient 做天空。**
   天空 = 3 段纯色横带 + 一条正弦叠加的远山剪影。
   连续渐变会立刻把画面拉到"廉价 3D 渲染"，而平涂分段才是原神那种"色块分明"。

3. **明度差就是空间关系。** 平涂风格里没有光影来交代前后，
   只能靠"墙面最暗 / 柱子中 / 窗最亮"这种 ≥25% 的明度阶差。
   这条和 G2 的"远亮近暗"结论是同一件事的两种表述。

4. **纵深靠"层与层的关系"，不靠对单层做变换。** 三个来源叠加：
   尺寸递减（`s=f/z`）+ 明度递减（远处更接近背景色）+ 雾化（远处蒙一层淡蓝）。
   **三个一起给才像真的**，只给一个都像贴图。

5. **画连续拱廊/柱廊/隧道时，拱洞只描边、不填充。**
   填充会让近处的拱挡住远处所有的拱（第一版 e113 就是这么崩的）。
   只描边 → 后拱透过前拱可见 → 纵深自然出现。

6. **层叠构件（拱券、线脚、扶壁）必须从最外层/最宽者开始画。**
   反过来画，最外层会把里面全盖住（e112 第一版只剩一个大拱）。

7. **金色必须垫暗底。** 金（`#d9b25e`）直接放蓝紫底上不够跳；
   先画一个压暗 42% 的暗色菱形/星形，再压金色上去 → 金色立刻"发光"。
   金线（`rgba(gold,0.3~0.55)`）描在拱缘/檐口上，是"精致感"最廉价的来源。

8. **用世界坐标 + 透视相机建模，不要手写像素坐标。**
   所有尺寸用"米"思考（塔高 13、门宽 3.8、窗台高 4.8），比例天然正确；
   换相机 `f` 就整体缩放，换 `vpy` 就从平视变仰视。
   **注意：任何用相机的场景，Z 必须 ≥1**（Z=0 会让 s=f/0.05 把坐标全部炸飞）。

## 两个工程教训（值得写进任何 Canvas 项目规范）

1. **`ctx.save()` / `ctx.restore()` 不配对 = clip 泄漏，且完全静默。**
   我在 `roseWindow` 漏了一个 restore，之后**所有绘制被裁掉**，
   画面表现只是"右半边莫名是空的"，无报错、无异常，极难定位。
   建议哨兵：
   ```js
   let __clipDepth = 0;
   ctx.save    = function(){ __clipDepth++; return __save(); };
   ctx.restore = function(){ __clipDepth--; return __restore(); };
   // 每张图结尾 __assertClip();
   ```
   **本组 e103/e108/e113 三次事故全部由它定位。**

2. **不要用正则去改图形代码。** 我用 `String.replace` 批量改 `roseWindow` 时
   连带删掉了一个 `ctx.restore()`（第 1 条的直接起因），
   还在 `archFullPath` 后留下一个多余 `}` 造成语法错误。
   **图形代码要用 edit 精确改，改完立刻 `node --check`。**

## 对 BRIEF 假设的验证

> **几何化 + 平涂 + 分层 + 冷暖** 是否足以复刻？

**在"建筑"这个子问题上：成立，且余量很大。**
- 哥特建筑确实高度几何化：拱 = 2 段贝塞尔，柱 = 矩形 + 梯形，花窗 = 圆并集。
  15 张图没有一张需要"手绘感"的笔触。
- 平涂（每块面 ≤3 个色阶）完全够用，e114 和参考图的接近程度主要来自
  "明度分层 + 平涂天空 + 金线"，而不是任何写实渲染。
- 真正的门槛不在"画得像"，而在**比例**：塔高/窗宽/层高之比一旦偏 10%，
  立刻从"教堂"变成"仓库"。用世界坐标建模是控制比例最有效的手段。

**代价与边界**：
- 单张 1920×1080 的代码量约 30–40KB（含库），生成一张约 1–2 秒。
- 复杂构件（玫瑰窗 12 瓣、层叠拱券 7 层）的**绘制顺序**是正确性关键，
  比几何本身更容易出错。
- 冷暖对比在建筑上只能靠"窗光（冷）+ 门内暖光（暖）"，
  建筑本身要维持冷调 —— 暖色是**视线锚点**，用多了就废了。
